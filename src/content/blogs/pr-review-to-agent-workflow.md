最近做 [Maka 的一个 PR](https://github.com/apache/maka/pull/5308)，我反复经历了同一种情况：一轮 review 指出问题，改完代码、补上测试；下一轮又发现，新改动让别的模块开始承担本不属于它的判断。测试也随着每轮修复增加。单看每次修改都有理由，连起来看，PR 却越来越难解释。

起初我以为自己需要的是一份更详细的设计报告。后来发现，报告写得再长，如果没有人持续核对它与代码的关系，照样会过期。我真正想解决的是：下次做 PR 时，怎样让 Agent 在每一轮修改中都记得回到原始需求，检查规则归属，并删掉已经不需要的东西？

最后，我把这次经验拆成两部分：写进 `AGENTS.md` 的常驻原则，以及负责具体流程的 [`pr-lifecycle` Skill](https://github.com/wutongyuonce/pr-lifecycle)。

## 先弄清 SPEC 到底写什么

这次讨论里，我一度把 SPEC 理解成一张规则清单。规则当然重要，比如“列表读取必须有界”“导入不能修改外部数据”。但几条规则拼在一起，还不足以说明整个功能。

完整的 SPEC 还得回答：谁在什么场景下操作？操作按什么顺序发生？失败时用户看到什么？哪些情况明确不处理？怎样验收？规则是其中一个部分，用来描述局部必须成立的事实。

这个区分很实际。PR 中有一段分页实现，曾经为“翻页时数据不能移动”提供了更强的一致性保证，随之需要维护额外状态、过期处理和数据库读事务。回头看原始需求，真正要守住的是有界读取、稳定顺序和不重复。把额外保证当成必需品，复杂度就会从底层一路传到协议和界面。

我现在会先把需求问清楚，再讨论技术方案。遇到含糊的地方，可以用 Grilling 沿着决策依赖追问：先确定用户目标和范围，再问失败、并发、资源限制。还没决定“要保证什么”时，先争论“用什么算法”，通常太早了。

## 设计报告要跟着 PR 一起变

SPEC 说系统必须做到什么，设计报告则说明由谁负责、怎样协作。两者都不应该被某个 commit 永久定格。

我希望设计报告在 PR 过程中始终描述当前实现。一次 review 让方案发生变化，就在同一轮修改中更新报告、代码和测试。如果旧方案已经撤掉，报告里也不该继续保留它的升级路径、临时脚本或中间状态。设计为什么改变，可以写在 review 回复或决策记录里；最终设计报告只需要让后来的人看懂现在的系统。

还有一点要警惕：代码已经变成另一套方案，再把报告改成替代码辩护的文字。每次设计调整都要回到 SPEC，说明原来哪项判断变了，新的取舍是什么。Issue、设计报告、代码和测试必须互相对得上。

## 一条规则，谁说了算

Review 中让我反复停下来的，是模块归属。一个模块读取外部数据，另一个模块管理导入，界面负责给用户选择；职责看上去都合理。但如果界面也根据列表变化推断“导入成功了”，或者两个入口各自决定哪些会话可选，同一条规则就有了两个答案。

于是设计报告里需要比“模块 A 负责 X”更具体的东西：每条规则、状态、错误和资源上限，由哪个模块最终决定？其他模块通过哪个接口取得结果？调用方为了正确使用接口，必须知道哪些顺序、错误和性能约束？

我不需要把每个函数都画进架构图。把决定权分清楚，很多判断就不用在多个调用方重复出现。修改规则时，也更容易知道该改哪里、该测哪里。

## Review 后先找义务，再动代码

我以前容易把 review 意见当成待办项：指出哪一行，就修哪一行。这个 PR 让我意识到，有些评论指出的只是症状。直接在被点名的位置加判断，可能让另一个入口继续保持旧行为。

现在我会先问几句：它违反了 SPEC 的哪项义务？这条规则的归属在哪里？还有哪些调用方走同一路径？Reviewer 建议的机制，是否比原需求要求的更强？想明白这些再改，往往能在真正负责的模块修一次，而不是在几个客户端分别补丁。

Reviewer 的具体建议仍是很有价值的线索。最终怎么改，还得对需求、现有架构和代价负责。

## 测试也需要定期删

每次修复都加测试，听起来很稳妥。问题是，测试可能只是在保护当时采用的一种机制。机制换了，旧测试仍在；同一条规则又在适配器、Host 和界面各测一遍。数量增加，并不能说明我们更了解最终行为。

我把后来的清理叫作“测试消融”。做法是先列出最终必须保证的行为，再为每项行为找到离规则归属最近、能在旧错误上失败的测试。跨模块测试只保留那些确实在验证接口协作的。已经废弃的方案、重复的断言、用巨大数据或运行耗时绕着证明同一个性质的测试，都值得重新检查。

删完之后，我希望每条保留下来的测试都能回答一个问题：如果这项义务被破坏，我会不会及时知道？

## 为什么拆成 AGENTS.md 和 Skill

这些经验如果只留在一篇博客里，下次写 PR 时我大概还是会忘。我也不想把几十条步骤全部塞进全局指令，让每个小修复都走一遍重流程。

所以我做了分层：`AGENTS.md` 留下常驻纪律，比如先明确契约、一条规则只有一个权威模块、修改时同步设计与测试、处理 review 要找根因；[`pr-lifecycle`](https://github.com/wutongyuonce/pr-lifecycle) 则在复杂 PR 中展开完整流程，从恢复事实、形成 SPEC、设计模块归属，到按义务实现、处理 review、最后做测试消融和一致性审查。项目自己的 `AGENTS.md` 与 `CONTRIBUTING` 仍决定具体命令和规范。

Skill 里还有 SPEC/设计报告模板，以及 review 与消融检查表。我希望 Agent 能据此产出可检查的东西，而不只是口头说“会注意边界”。小修复可以裁剪步骤；涉及多个模块、持久化或协议的 PR，就值得把这些问题认真写下来。

这套流程还需要在后续 PR 里检验。它不会替我做产品取舍，也不能替代维护者的 review。对我来说，它目前最有用的一点很朴素：每次又想加一个状态、错误码或测试时，先停下来问，这到底对应 SPEC 的哪项义务？
