## 1. 这功能到底在解决什么

你在 Claude Code 里已经聊过一轮：改过文件、问过为什么报错、模型也给过一段还算能用的结论。过几天你改用 Maka。问题不是把聊天记录复制粘贴过来，而是那份对话还躺在另一个程序的本地文件里。

Claude Code、Codex、OpenCode 都会把会话写到自己的目录。格式不一样，字段也不一样。有的是一行一条 JSON 的日志，有的是 SQLite。它们本来是给原程序 resume 用的：下次打开，还能接着上次的上下文说话。

Maka 也有自己的会话。它不会去改别人的文件，也不会假装自己就是 Claude Code。它要做的更窄：

```text
选中别人的一份旧对话
→ 在 Maka 里生成一份自己的任务
→ 以后你在 Maka 里接着发消息
```

这份任务是快照。导入完成以后，外部文件再增加新消息，已经导入的那份不会跟着变；你在 Maka 里继续聊，也不会写回 Claude Code。同一份外部对话导两次，会得到两份互相独立的 Maka 任务，谁也不覆盖谁。

这听起来像复制。难的是复制对象不是一段纯文本，而是另一个运行时留下的执行痕迹：用户话、助手回复、工具调用、压缩记录、子会话，再加上大量 Maka 当前并不执行的元数据。导进来以后，用户得看见原来的对话；下一次发给模型时，又不能把对方运行时的工具记录，当成 Maka 此刻刚执行过的步骤。

## 2. 需要先知道的几件事

打开 Maka 任务列表里的一项，看到的就是一份会话：一次连续对话的全部记录。Claude Code 的一份 JSONL、Codex 的一条 thread、OpenCode 的一个 root session，也是这个意思。

原程序按自己的格式把会话重新加载，叫 resume。导入不是 resume。resume 还在原来的程序里；导入是换到 Maka 的存储和执行链上。

选择列表叫 catalog。它只需要标题、时间、工作目录，够你认出“就是那一次”。点导入之后，才去读完整记录。Claude Code 常用 JSONL，也就是一行一个 JSON 对象。如果列表阶段把整个文件读进内存，会又慢又危险，所以摘要和全文必须分成两种读取预算。

TUI 和桌面应用都连同一个 Runtime Host。会话存在哪、导入有没有成功、现在有几份副本，都以 Host 为准。远程 Host 读的是它自己机器上的来源文件，不会去翻你笔记本上的 `~/.claude`。

## 3. 以前为什么会裂成两套

PR 之前，Desktop 已经能把外部历史变成原生 Maka 会话。TUI 走的是另一条路：在本地扫文件，建一个空会话，再把旧对话摘要包成隐藏 prompt 发给模型。

Desktop 得到的是一份真正落库的历史。TUI 得到的是一个新 Agent，外加一段有损摘要，而且导入当下就会打一次模型。同一个 OpenCode 会话，两端结果对不上。有人还想给 TUI 那套扫描器再接 OpenCode，等于同一份数据要被第三套代码解释一遍。

[#5053](https://github.com/apache/maka/issues/5053) 把方向定死了：不要给旧扫描器加来源，把 TUI 的特殊语义删掉。两个界面都通过 Host 的 catalog / import 选一份、导一份。维护者后来确认了三条：

- 超限就整次拒绝，不发布“看起来还能用”的半截历史；
- TUI 复用 Host 分页目录，不再自己限制“最近 30 天、最多 50 条”；
- 同一个 PR 接通新路径，同时拆掉旧扫描器和 digest handoff，不留并行中间态。

[#5308](https://github.com/apache/maka/pull/5308) 就是这条决定的实现。2026-09-16 合并，70 个文件，+5505 / -3576。导入过程不调用模型；下一次你主动发消息，才走普通会话执行链。

## 4. 用户侧实际发生了什么

打开 TUI 或 Desktop 的导入界面后，顺序很短：

```text
1. 看当前 Host 能发现哪些来源
2. 选 Claude Code / Codex / OpenCode
3. 翻一页摘要，需要的话按当前项目筛，或者搜标题、路径、来源 ID
4. 选中一条
5. 点导入
6. 得到一个新的 Maka 任务并打开它
```

来源在、会话在，不等于已经被导入。检测到来源只表示“这个程序的数据能读”，一次导入始终针对你点名的那一条。

列表和任务列表也不是同一张表。catalog 列的是别人的会话；Maka 任务列表列的是已经发布的原生任务。一份很久以前的对话导进来后，不一定出现在任务列表顶部，因为任务按对话活动时间排。刚导入的旧会话，活动时间往往也很旧。

如果这条来源以前导过，界面不会把“再导一次”偷偷改成“打开旧的”。Desktop 行上分开两个动作：打开最近那份已发布任务，或者再次导入。TUI 对已有副本给出菜单：打开最近导入的任务、再次导入、取消。打开用的是 Host 当前返回的最近 ID，不会把一次结果不明的请求，事后安到某条任务头上。

结果不确定时，界面只留警告，让你去任务列表自己看。它不会宣布成功，不会宣布失败，也不会自动再导一次。你明确再点一次导入，那是一项新操作。即便上次其实已经成功，这次也可能再产出一份副本。

进行中的重复点击是另一回事。同一次导入还没结束时，Host 把后续请求并到同一个进行中的操作上，避免双击、多窗口、TUI 和 Desktop 同时点，落出两份要靠肉眼分辨的任务。这个合并只覆盖“还在飞”的请求。飞完之后再点，就是新快照。

## 5. 其他 Agent 可以先拿走的设计

下面这些不依赖 Maka 的类名。任何要把“别人的会话”接进自己产品的 Agent，几乎都会撞上同一组问题。

### 5.1 核心原理

**导入是快照，不是同步。** 一旦做成持续同步，你就要回答来源更新了怎么办、两边都续写了怎么合并、旧副本算不算过期。Maka 直接不做：来源只读，已发布副本不再跟随来源，Maka 的新消息也不写回去。重复导入不覆盖、不合并。用户要的如果是另一条工作分支、另一个模型，就再导一份。

**给用户看的列表，和已经变成自己任务的列表，必须分开。** catalog 回答“外面有什么可选”。任务列表回答“我这边已经有哪些可用会话”。用同一张表去承担两件事，就会出现“刚导入却找不到”、或者把别人的文件误当成自己的任务。

**给用户看的历史，和发给模型的历史，也可以不是同一段。** 来源如果真的以助手回复开头，界面仍应保留原样。Anthropic 这类接口却要求对话由 user 开头。正确做法不是导入时砍掉助手前缀，而是在“准备发给模型”的那一层，从第一个对模型可见的 user 边界开始投影。用户看见完整原件；模型收到合法序列。

**“结果未知”是一种结果，不是失败的修辞。** 持久化一旦开始，客户端可能收不到最终回包。这时既不能当成功自动打开，也不能当失败自动重试。自动重试会在其实已经成功时再写一份；自动打开会把别人刚导入的副本，误认成自己这次的产物。未知就是未知：去已发布列表里看，或者明确再做一次新操作。

**完整或拒绝。** 超限、损坏、只有工具记录没有对话，都在发布前失败。不要默默丢掉旧内容、只留最近一段，还对外宣称导入成功。部分历史一旦发布，就要另做一套“不完整”的产品语义。Maka 选择现在不做。

**一条业务规则只放在一个地方。** 来源格式变化时，只应该改读这个来源的适配器。分页游标怎么往下走，也只能由真正理解排序键的那一侧决定。界面如果自己解析错误字符串、自己猜哪条任务属于哪次请求，规则很快会在 TUI 和 Desktop 上各长一套。

### 5.2 推荐链路

```text
界面：只选来源和会话
    ↓
主机：解析当前项目、分页查询、处理并发、给结果分类
    ↓
适配器：用有界读取返回一页摘要；用户选定后再读完整记录并转成宿主消息
    ↓
导入器：确认存在可阅读的对话，规范化标题和时间，再进入暂存
    ↓
账本：把历史物化成宿主自己的执行记录
    ↓
发布：任务出现在列表里，界面打开返回的那一个 ID
    ↓
用户下次主动发消息：模型才基于这份历史继续
```

catalog 读摘要，import 读全文，published 才能打开。三步不要并成一步。列表阶段读全文，选择器会把整个来源库拖进内存；导入阶段只读摘要，发布出来的任务会是空的。

### 5.3 模块权威

| 规则 | 谁说了算 | 别人可以做什么 |
| --- | --- | --- |
| 文件怎么找、字段怎么解、一页从哪续 | 对应来源的适配器 | 调用“下一页 / 读这一份”，不要解码游标 |
| 搜索、路径是否算同一个项目、标题怎么消毒、上限种类 | 跨来源的共享契约 | 适配器实现它，不要各自发明一套匹配 |
| 当前项目怎么解析、导入是否合并、暂存和发布、错误码 | 主机上的导入协调器 | 界面只展示这些结果 |
| 已经发布了几份副本、最近那几个任务 ID | 会话存储 | 主机把它投影到列表项上，客户端不要自己数文件 |
| 存下来的历史能不能发给当前模型 | 回放 / 投影层 | 发送、压缩、摘要走同一条默认规则 |
| 按钮、警告、打开哪一个 ID | 各客户端 | 只本地化主机结果，不把“多出来的任务”归因到未确认请求 |

这条表的用处是防漂移。OpenCode 改 schema 时，不该让 TUI 和 Desktop 各补一个解析器。游标过期时，不该有的界面当存储失败，有的界面当用户点错。未知结果时，不该 Desktop 锁住一行、TUI 直接允许再点。

评审后期也是按这个方式收口的：不再逐条修“这个函数漏了”，而是先写不变量、指定唯一 owner、把所有消费者审一遍。投影必须从 user 边界开始，就应该是投影层的默认行为，而不是每个调用方记得打开一个开关。

## 6. Maka 里这些原理是怎么落地的

### 6.1 四个包，四种职责

跨来源契约放在 `packages/core/src/external-session.ts`。它认识查询、标题消毒、cwd 边界、路径是否算同一个项目、以及 `listSessionPage` / `readSession` 这两个接口。它不认识 Claude 的 JSONL，也不认识 Codex 的 `state_N.sqlite`。

三个 storage adapter 各自拥有发现、筛选、分页、解码和转换成 Maka `StoredMessage[]` 的规则。Host 的 `HostExternalSessionCoordinator` 拥有 workspace 解析、wire 校验、进行中合并、暂存发布和稳定错误码。TUI runner 与 Desktop 设置页只负责选、提交、按结果码更新按钮。

旧的 TUI scanner、`foreign-session` 和 digest handoff 在这个 PR 里从生产路径删除。来源格式不再有第二套读者。

### 6.2 列表必须有界，游标必须不透明

Host 和客户端把 catalog cursor 当成不透明字符串。格式错了、属于另一次查询、或者已经续不下去，适配器抛 `ExternalSessionCatalogCursorError`，Host 映射成 `invalid_request`。扫描候选超过上限则是 `source_limit_exceeded`。两种失败不能混。

Host 最多向适配器要 `page size + 1` 项。每一项都带着“我后面那一格”的来源 cursor。页面字节预算截断时，下一页从最后真正交给客户端的那一项之后继续。被丢掉的非法行、没放下的超预算行，都不能让下一页跳行。

Claude catalog 对每个候选最多读 256 KiB 头和 256 KiB 尾。窗口边缘的半截 JSONL 不当完整记录。项目目录名不是 cwd 的可逆编码，`-workspace-my-project` 无法区分 `/workspace/my-project` 和 `/workspace/my/project`。带 workspace 条件时，只接受有界头部里完整读到的顶层 `cwd`；读不到就缺席，而不是猜进当前项目。

OpenCode 导入有三道上限：编码字段合计 64 MiB、解码后的 message/part 25 万行、转换后的 canonical 消息 256 MiB。任一超限，提交前整次拒绝。catalog 只收能确认 `parent_id` 为空的 root；child、类型不合法、无法确认的行全部 fail closed。

Codex 不在 Host 里保存跨请求的 snapshot、TTL 或 LRU。评审里一度出现过“打开选择器就钉住来源 WAL 五分钟”的方案，最后被拿掉。现在是无服务端状态的 keyset：state DB 按 `(sort_key DESC, id DESC)`，文件系统 fallback 按 `(mtime DESC, 相对路径 ASC)`。`sort_key` 由查询算一次、随行选出、再原样写进 cursor，避免 SQL 排序和 JS 游标各算各的。首页只读最新的 `state_N.sqlite`。这一代读不了，就改走文件系统，而不是退到更旧的 generation。更旧那本是上次跃迁时冻结的快照，跃迁之后新建的会话都不在里面。续页必须还指向发出它的那一代；原文件没了就让 cursor 失效，而不是偷偷换语料。

keyset 放弃的是“翻页中途被更新的行留在旧位置”。两页之间一条 live session 若更新并排到了 cursor 前面，这一趟可能看不到它，但不会把已经交付的行再送一次。重新打开列表会看到当前顺序。Claude 和 OpenCode 的 offset 分页同样不承诺实时快照。

### 6.3 什么东西才算“可导入的对话”

导入器和 Ledger 共用 `isConversationTextMessage`：user 算对话；assistant 只有非空文本才算；tool、note、token、turn-state、steering 单独不能构成对话。转换结果如果只剩运行元数据，会在创建暂存会话之前失败，避免任务列表里出现一个空壳。

来源工具协议可以在转换时参考，但不是 Maka 下一次 provider replay 的执行权威。导入不会把外部 tool record 伪装成当前运行时刚刚执行过的步骤。

Ledger 修复按每个 turn 的最后一条记录结算状态。turn 交错、同一 turn 有多条状态时，先分页找到各 turn 的最后序号，再按固定 high-water 转换同一份 transcript。最终状态以最后一条状态记录为准。

### 6.4 暂存、发布、恢复

校验和 catalog 投影在宣布持久化开始之前做完。然后创建 `transcriptLedgerVersion: 0` 的暂存会话。Ledger 物化成功后才发布。物化前失败就删暂存。Host 启动时 `recover()` 继续处理版本 0 的会话。只有已发布副本计入 `importedCount`。归档仍算；删除和仍在暂存的不算。

`importedCount` 是仍存在的全部已发布副本数。`importedSessionIds` 只带最近几个对 wire 安全的 ID，给“打开最近一份”用。它可能包含另一个客户端刚导入的任务，所以不能用来对账某一次未确认请求。

### 6.5 稳定错误，客户端不猜

适配器出类型化错误，Host 映射成公开结果，客户端只做文案：

| 结果 | 含义 |
| --- | --- |
| `source_limit_exceeded` | 完整导入或 catalog 扫描碰到明确上限 |
| `model_unavailable` | 当前没有能给新会话用的模型配置 |
| `source_unreadable` | 来源文件、记录或转换内容读不了 |
| `commit_outcome_unknown` | 已经进入持久化，最终结果无法确认 |
| `invalid_request` | 游标非法、查询对不上，或者 workspace 已失效 |
| `not_found` | 列表和导入之间，来源会话消失了 |

`commit_outcome_unknown` 和“请求已派发但传输中断”是同一种语义。TUI 和 Desktop 都必须按未知处理。未知不自动重试；用户再点一次，是新操作。

### 6.6 发给模型时的 user 边界

Ledger 会忠实保存 assistant-first 的原件。`buildRuntimeEventModelReplayPlan` 用 durable 的 `storedMessageId` 认出 repair 回填出来的助手前缀，默认从第一个对模型可见的 user 事件开始投影。continuation 另有准入。原生旧会话和导入会话走同一条规则，避免“只给导入修、本地历史继续 400”。

评审里验证过更粗的规则——丢掉第一个 user 之前的一切。那会把普通发送路径打坏：折叠或预算裁切后的上下文，本来就可以从 assistant 事件开始。所以删除范围必须限定在 repair 回填，而不是所有前缀。

## 7. 明确不做的事

这套设计不追踪来源更新，不给已导入会话做增量同步，不增加 freshness 状态机，不迁移旧 digest handoff 留下的普通会话，不发布被截断的部分历史。未知结果也不靠跨客户端 attempt ID 自动对账。

它也不承诺：对一份正在被 Codex 写入的实时数据库做跨页快照；打包后的 Desktop 和真实并发写入的外部客户端，当时都没有做端到端验证。

## 8. 若要在自己的 Agent 里做类似的事

先写用户契约，再写类。契约可以短成六句：

1. 用户点哪一条，就只导哪一条。
2. 每次明确导入都是新快照。
3. 导入当下不打模型。
4. 来源只读。
5. 失败要么完整拒绝，要么承认未知；不要静默部分成功。
6. 两个界面看到同一份已发布结果。

然后把格式、分页、发布、投影、按钮分成五个 owner。格式变化时只改适配器；发布规则变化时只改主机；模型能不能吃这段历史，只改投影层。客户端如果开始解析来源文件，或者根据“副本是不是刚好 +1”猜测刚才那次点击的命运，这套设计就已经在裂。

Maka 的特殊之处在于它已经有 Host、Ledger 和 Desktop/TUI 两套界面。换到只有一个 CLI 的 Agent，主机和界面可能叠在同一个进程里，但权威仍然不该叠：读别人的 JSONL 是一件事，把自己的会话标成可用是另一件事，决定下一轮 prompt 里放哪些消息是第三件事。PR #5308 真正值得抄的，不是某一个 adapter 的字段表，而是这三件事没有再被写进两套代码里。
